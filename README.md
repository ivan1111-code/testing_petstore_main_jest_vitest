# Тестирование Petstore Swagger v2 на Jest и Vitest

Проект демонстрирует API-тесты для публичного [Swagger Petstore v2](https://petstore.swagger.io/v2)
на двух JS-раннерах: **Jest** и **Vitest**. Набор тестов покрывает ресурсы
`pet`, `store`, `user` (positive + negative, параметризация)

# Контрольные вопросы
1. Для чего предназначены модульные тесты?
--------------------------------------------------------------------------------
Модульные (unit) тесты проверяют изолированную единицу кода — функцию, класс,
модуль — в отрыве от внешних зависимостей (БД, сети, файловой системы).
Цели:
  - быстро поймать регрессии при рефакторинге;
  - зафиксировать контракт функции (вход -> выход);
  - документировать поведение;
  - дать уверенность при изменении кода.
Внешние зависимости заменяются моками/стабами, чтобы тест был детерминированным
и быстрым.


2. Чем отличается Jest от Vitest?
--------------------------------------------------------------------------------
Jest:
  - CJS по умолчанию, ESM через Babel или --experimental-vm-modules;
  - требует babel.config.js и jest.config.js;
  - медленнее на больших проектах;
  - зрелая экосистема, стандарт де-факто;
  - моки через jest.fn().

Vitest:
  - ESM нативно, без Babel;
  - один vitest.config.js;
  - быстрее за счёт Vite/esbuild;
  - watch-режим по умолчанию;
  - API совместим с Jest (describe/test/expect/test.each);
  - моки через vi.fn();
  - особенно удобен в Vite/Vue/React-проектах.

Ключевое: API почти идентичен, разница — в инструментах сборки и скорости.


3. Что такое параметризация тестов?
--------------------------------------------------------------------------------
Это запуск одной и той же логики теста с разными входными данными, где каждый
набор параметров становится отдельным тест-кейсом в отчёте.

  pytest:      @pytest.mark.parametrize("data", [1, [2], "3"])
  Jest/Vitest: test.each([1, [2], "3"])("... %j", async (data) => {...})

Плюсы: меньше дублирования, единый сценарий, наглядный отчёт по каждому кейсу.


4. Чем интеграционные (API) тесты отличаются от модульных?
   Для чего нужны моки (jest.fn / vi.fn, nock, MSW)?
--------------------------------------------------------------------------------
Модульные тесты проверяют одну единицу в изоляции, зависимости заменены моками.
Интеграционные (API) тесты проверяют взаимодействие нескольких компонентов:
HTTP-клиент -> сеть -> сервер -> БД -> ответ. Они проверяют контракт API
(статусы, схемы, коды ошибок), а не внутреннюю реализацию.

Моки нужны, чтобы:
  - изолировать тест от реальной сети/БД (детерминизм, скорость);
  - симулировать редкие сценарии (500, таймаут, битый JSON) без реального
    сервера;
  - проверить, что код вызвал зависимость с нужными аргументами
    (toHaveBeenCalledWith).

В нашем проекте моки не используются — тесты идут против живого Petstore
(это интеграционные API-тесты). Моки пригодились бы, если бы Petstore был
недоступен или нужно было бы проверить обработку 500/таймаута.


5. Почему важно проверять не только тело ответа, но и статус-код и структуру
   данных? Почему тесты против публичного API могут быть нестабильными (flaky)?
--------------------------------------------------------------------------------
Статус-код — первый контракт: 200 vs 404 vs 500. Тело может быть валидным
JSON, но с кодом ошибки.

Тело — бизнес-данные: name, id, status. Без проверки тест пройдёт, даже если
сервер вернул чужой объект.

Структура (наличие полей, типы) — контракт схемы. Поле может пропасть при
рефакторинге API, и клиент сломается.

Flaky тесты против публичного API — потому что:
  - mock-сервер petstore.swagger.io нестабилен: падает, отвечает 502/503,
    иногда теряет данные;
  - сетевая задержка -> таймауты;
  - общее состояние между прогонами (другие пользователи создают/удаляют
    питомцев с теми же id);
  - rate limiting;
  - разное поведение (например, uploadImage без файла -> 415 или 500);
  - Jetty отдаёт HTML на невалидные URL, а приложение — JSON.

Поэтому в тестах ослаблены некоторые проверки ([200, 500], in (400, 404)),
а прогон идёт последовательно (maxWorkers: 1 / fileParallelism: false).


6. Как выполняется запуск тестов в Node.js? (укажите, в какой IDE работаете)
--------------------------------------------------------------------------------
Запуск — через npm-скрипты или напрямую:

  Jest:
    npx jest
    npx jest tests/pet.test.js
    npx jest -t "Add a new pet"
    npm test

  Vitest:
    npx vitest run
    npx vitest run tests/pet.test.js
    npx vitest run -t "Add a new pet"
    npx vitest            # watch
    npm test

В IDE:
  VS Code — расширения Jest (Orta) и Vitest (Vitest Official) добавляют
    кнопки запуска рядом с test(...), панель Test Explorer, запуск/отладку
    одного теста, показ diff при падении. Встроенный debugger (launch.json
    с "type": "node") позволяет ставить breakpoint'ы в тестах.
  WebStorm / IntelliJ IDEA — Jest и Vitest поддерживаются из коробки:
    gutter-иконки запуска, отдельная панель Run, coverage, отладка.
  CLI — npm test в терминале IDE или отдельном терминале.

В нашем проекте использовался VS Code + терминал: npm test в каждом из
каталогов jest/ и vitest/.


7. Что общего между Jest и Pytest?
--------------------------------------------------------------------------------
  - Оба — тест-раннеры с автообнаружением тестов (test_*.py / *.test.js).
  - Структура: describe ~ класс/группа, test ~ def test_*.
  - Ассерты: expect(x).toBe(y) ~ assert x == y;
    expect([...]).toContain(x) ~ assert x in [...].
  - Параметризация: test.each ~ @pytest.mark.parametrize.
  - Фикстуры: beforeEach/afterEach/beforeAll/afterAll ~ @pytest.fixture
    (yield), setup_method/teardown_method.
  - Маркеры/теги: test.skip/test.only ~ @pytest.mark.skip/xfail.
  - Отчёты: оба умеют JUnit XML, оба интегрируются с Allure.
  - Запуск по имени: jest -t "name" ~ pytest -k "name".

Различие: pytest умеет yield-фикстуры (код до yield — setup, после — teardown),
Jest/Vitest — только колбэки beforeEach/afterEach.


8. В чем преимущества Vitest?
--------------------------------------------------------------------------------
  - Нативный ESM — не нужен Babel/ts-jest, меньше конфигов.
  - Скорость — Vite/esbuild, быстрый старт, HMR в watch-режиме,
    параллельные воркеры.
  - Совместимость с Jest API — describe/test/expect/test.each работают
    как есть, миграция простая.
  - Единый конфиг с Vite-проектом (vitest.config.js наследует vite.config.js).
  - Встроенный coverage (v8 / istanbul) без доп. пакетов.
  - Удобный watch по умолчанию, фильтрация по имени файла/теста.
  - vi API для моков, таймеров, шпионов — гибче и современнее.
  - TypeScript из коробки без настройки.


9. Для каких задач может быть интересен встроенный раннер node:test?
--------------------------------------------------------------------------------
node:test — модуль из стандартной библиотеки Node.js (с 18+), без зависимостей.

Интересен, когда:
  - не хочется тащить Jest/Vitest в маленький проект/скрипт/CLI-утилиту;
  - минимум зависимостей — безопасность, размер node_modules, supply-chain;
  - простые unit-тесты без сложных моков и снапшотов;
  - тестирование самого Node-кода (fs, streams, http) — раннер уже встроен;
  - CI с жёсткими требованиями к аудиту зависимостей;
  - быстрый smoke-тест в репозитории без настройки сборки.

Ограничения: меньше экосистемы (нет такого количества матчеров, репортеров,
интеграций с IDE), нет снапшотов "из коробки", параметризация менее удобная
(test.each отсутствует, циклы вручную). Для больших проектов Jest/Vitest
всё ещё удобнее.
